# /release - Tag a release with a proper changelog

Create a versioned release with a changelog derived from actual commits and PRs, not guesswork.

## Usage

```
/release              # auto-detect version bump from commits
/release patch        # force patch bump
/release minor        # force minor bump
```

## Steps

### 1. Gather raw material

Read ALL commits and merged PRs since the last tag:

```bash
LAST_TAG=$(git describe --tags --abbrev=0 HEAD)
# Full commit messages (subject + body)
git log --format="%h %s%n%b" "${LAST_TAG}..HEAD"
# Merged PR numbers
git log --format="%s" "${LAST_TAG}..HEAD" | grep -oP '\(#\d+\)'
```

For each merged PR number, fetch the PR title and description:

```bash
gh pr view <number> --json title,body,labels --jq '{title,body,labels}'
```

Read the first line of every commit. When a commit message has multiple lines, read all of them. When a commit references a PR (`(#N)`), the PR description often has better context than the commit message.

### 2. Classify changes

Sort every change into one of these categories:

- **Features**: new user-facing capability (maps to MINOR bump)
- **Fixes**: bug fixes, corrections (maps to PATCH bump)
- **Improvements**: performance, UX polish, non-trivial refactors visible to users
- **Infrastructure**: CI, deployment, tooling, docs (no bump on its own)

If the user didn't specify patch/minor, decide:
- Any items in Features? -> MINOR
- Only Fixes/Improvements/Infrastructure? -> PATCH
- Only Infrastructure? -> probably skip the release, ask the user

### 3. Write the changelog

Write a human-readable changelog. Not a commit dump. Group by category, describe what changed in plain language. One line per change. Reference PR numbers.

Example format:
```
## What's new
- Interactive antenna placement optimizer with grid search (#389)
- Base station data for France and Germany (#391, #392)

## Fixes
- Fixed compliance heatmap crash at frequencies below 6 GHz (#395)

## Improvements
- 3x faster spatial averaging matrix construction (#393)
```

### 4. Update the feature inventory

Read `docs/internal/features.md`. For each item in the **Features** category from step 2, check if it should be added to the feature inventory. The bar: it must be a user-facing capability, not a minor improvement or bug fix. It has to fit the existing style (one bullet point, brief).

If features were added:
- Add them under the correct category heading in `docs/internal/features.md`
- Update the version label at the top of the file to the new version

If no features were added, just update the version label if it is stale.

### 5. Update release metadata

Run the existing metadata updater:

```bash
bash .claude/hooks/update-release-metadata.sh
```

This updates README.md (bibtex version, test count badge) and CITATION.cff (version, date-released).

### 6. Commit and tag

```bash
git add docs/internal/features.md README.md CITATION.cff
git commit -m "Update release metadata for vX.Y.Z"
git tag vX.Y.Z
git push origin master --tags
```

The `release.yml` workflow handles the rest: full test matrix and GitHub release with auto-generated notes.

## Rules

- NEVER guess what changed. Read the actual commits and PRs.
- NEVER pad the changelog with trivial items to make it look bigger.
- NEVER skip the feature inventory check. Even if you think nothing qualifies, scan the Features list.
- The changelog goes in the GitHub release body (auto-generated by release.yml, but the tag message can include it too).
- Follow the versioning rules in `.claude/rules/git-workflow.md`: patch for fixes, minor for features, major only when the user says so.
