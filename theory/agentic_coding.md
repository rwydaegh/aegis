Scaling Agentic Workflows in Scientific Computing: A Comprehensive Architecture for Long-Term Claude Code ProjectsThe intersection of advanced artificial intelligence and scientific computing necessitates a profound shift in software engineering paradigms. For complex, computationally heavy domains such as electromagnetic dosimetry, the reliance on AI-assisted development introduces unique scaling challenges. A codebase containing approximately 6,000 lines of Python across nearly fifty source files—such as the AEGIS library currently under development at Ghent University—represents a critical inflection point in the software lifecycle. At this nascent stage, the initial velocity gained through conversational AI programming, colloquially termed "vibe coding" within the developer community, frequently decays into architectural drift, technical debt, and context amnesia if rigorous, systematic guardrails are not established.The phenomenon of "strangulation" in long-term AI projects occurs when the autonomous agent is permitted to make compounding architectural assumptions without a persistent, stateful memory system or strict deterministic boundaries. Generative models are inherently optimized for probabilistic token prediction based on the immediate context window, not for maintaining long-term project state or enforcing rigid mathematical invariants across multi-session lifecycles. Practitioner reports highlight that while unstructured AI assistance can accelerate initial development, it often results in accumulating technical debt at extreme velocities, leaving the human developer managing a codebase they no longer fully comprehend. To successfully transition the AEGIS project from rapid prototyping to a production-grade scientific software suite capable of integrating multiple fidelity levels, ray tracing engines like DiffeRT, and advanced 3D visualization features, the development environment must be fundamentally restructured. This report details a comprehensive, expert-level architecture for managing long-term Claude Code projects, ensuring that the agentic workflow remains mathematically rigorous, contextually aware, and structurally sound as the repository scales.The Economics of the Context Window and Session ManagementTreating the context window as a finite, highly valuable resource is the single most impactful operational shift required for scaling AI-assisted software projects. As the AEGIS repository grows toward tens of thousands of lines of code, carelessly dumping entire files or relying on the agent to autonomously index the entire repository for every minor query will result in severe context bloat. When context utilization approaches upper thresholds, the system's reasoning capacity degrades, older instructions are aggressively compressed, and the agent begins to hallucinate non-compliant design patterns or forget established architectural rules.Telemetry Implementation via Custom Status LinesTo manage context effectively, absolute visibility into the agent's memory utilization is required. Claude Code supports the configuration of a custom status line via a shell script integrated into the ~/.claude/settings.json file, providing real-time telemetry on context consumption, model usage, and repository state directly within the terminal interface.Advanced implementations utilize command-line JSON processors, such as jq, to parse the continuous data stream piped via standard input from the Claude Code process. By extracting parameters such as the context_window.used_percentage, and combining this with native Git commands to count untracked, modified, and staged files, the developer maintains total situational awareness without interrupting the workflow. The community has developed open-source packages such as ccstatusline to standardize this display, offering visual progress bars that transition from green to red as the context window fills, alongside explicit token counts and active model indicators. Maintaining this constant visibility ensures the developer recognizes exactly when the context window is saturated and requires deliberate compaction.Session Chunking and Handoff ProtocolsA primary failure mode in prolonged AI development is the loss of project state when a session must be terminated due to context exhaustion. This forces a restart that wipes all working memory, requiring the developer to spend valuable time re-establishing the operational baseline. To scale the AEGIS library without losing the narrative thread of complex feature implementations, session handoff protocols must be rigorously standardized.The implementation of a Session Handoff skill automates the generation of structured transfer documents, completely decoupling the project's state from the ephemeral context window of a single session. Currently, the AEGIS project relies on a single 120-line CLAUDE.md file. To resolve this, the memory architecture must be decentralized using recursive import syntax and directory-specific scoping.The root instruction file should be aggressively condensed, containing only the project identity, the absolute core mandates, and imports to specialized rule files. The AEGIS repository should adopt a hierarchical .claude/rules/ directory structure. This ensures that the documentation regarding the Flask and Three.js 3D viewer, or the Playwright CLI visual QA commands, is only injected into the context window when the agent is actively modifying the frontend visualization subpackages. Similarly, mathematical constraints and tensor operation rules can be strictly scoped to the kernels/ and coherent/ directories, keeping the baseline context window pristine.Navigating the Auto-Memory SubsystemBeyond user-defined instructions, Claude Code utilizes an autonomous memory system that continuously accumulates operational knowledge. This system operates via a localized file, typically stored at ~/.claude/projects/<project-path>/memory/MEMORY.md, which the agent proactively updates with debugging insights, environmental quirks, and workflow habits.The distinction between user-defined prescriptive rules and the agent's descriptive auto-memory is critical for long-term project hygiene. The user-defined files serve as the immutable constitution of the project, dictating architectural standards and testing philosophies. The auto-memory serves as the agent's operational scratchpad, recording ephemeral lessons such as specific background server teardown procedures on Windows.Crucially, the auto-memory system enforces a strict 200-line loading limit. If this directory becomes polluted with obsolete debugging steps or incorrect assumptions made during a failed implementation attempt, it can silently induce unexpected behaviors. However, when applied to robust internal tools or scientific libraries with dozens of interacting classes, this unstructured approach is universally condemned by experienced software architects. To prevent the AEGIS library from devolving into an unmaintainable state, the workflow must strictly and immutably separate the planning phase from the execution phase.Enforcing Plan Mode for Complex ArchitecturesClaude Code provides a dedicated "Plan Mode", accessible via specific terminal flags, which explicitly restricts the agent to read-only operations.
